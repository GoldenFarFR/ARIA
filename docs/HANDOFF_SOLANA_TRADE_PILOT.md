[CODE] Subject : a PARTIAL sell was reported as a complete one -- the row closed, the tokens stayed, the PnL was fiction
Date : 2026.08.22 / Probleme : found by the operator against his own wallet, not by any check of ours. A liquidation printed "32 sold, 0 unsellable" while the chain verification in the SAME output listed three tokens still held -- two of them already marked closed in the pocket's table at +16.2% and -9.8%, PnL that never happened. Three defects stacked, each hiding the next. (1) `_swap_out` returned `units_sold=amount_units`, i.e. what it ASKED to swap, never what moved. (2) Worse, `out_amount` came from `quote["outAmount"]` -- the Jupiter QUOTE, not the executed transaction, so a fill up to 10% away from the estimate (the project slippage ceiling) was reported as fact. (3) The pocket closed the row on the mere presence of a tx hash, never checking anything was left. Sells run at COMMITMENT_SENT for latency, so nothing downstream ever looked at the chain either. Net effect: a partial fill stranded the remainder invisibly AND recorded a fictional closure, and no test could catch it because every component worked exactly as written.
Solution : the chain settles the question, never the quote. `_swap_out` now returns `units_requested` + `quoted=True` (the old key name WAS the false claim), and `execute_real_sell` calls the new `_settle_exit`, which re-reads the balance after the swap and reports `units_sold` as held_before minus held_after, plus `fully_exited`/`partial`. Three polls at 0.25/0.50/0.75s absorb the `sent` lag: the transaction is already gone, so this delays the REPORT and never the fill -- the ~90ms exit path is untouched. Unknown stays UNKNOWN: an unreadable balance returns `fully_exited=None`, and the pocket treats only an explicit `partial=True` as a blocker (treating unknown as failure would reopen good exits forever on a slow RPC -- reconciliation already owns that case with no deadline). A partial exit leaves the row OPEN and takes the same 30s cooldown as a failed sell, so the stranded position cannot be hammered on every pass (the 847-error outage of the same day). Seven tests, one replaying the operator's exact case. Not yet run against real money: trading is stopped, delegate key aside. — `solana_agent_wallet.py`, `solana_late_bonding_shadow.py`, `tests/test_solana_agent_wallet.py`, `tests/test_solana_late_bonding_real_cycle.py`.

[CODE] Subject : real trading loses -10.5% where the simulation shows +35% -- the gap is EXECUTION LATENCY, measured not theorised
Date : 2026.08.22 / Probleme : nine real trades against 49 shadow closures in the same epoch: -10.49% PnL and 11.1% winrate real, versus +35.05% and 73.5% simulated. Timestamps showed why -- 12-13 seconds, consistently, between sending the swap and recording the position. The shadow assumes an INSTANT fill; on a bonding curve that has just crossed 70%, thirteen seconds is enough for the price to gap 10% before the position is even tracked. Every closure carried the same signature: "filled at market, price had gapped below", 14-25 second round trips, eight losses in nine. Explanations ruled out first, each with data: the paid price equals the modelled price exactly (`entry_price == realistic_entry_price`, 0.0% difference), so neither impact nor slippage is involved, and it is the same pocket and the same candidates, so it is not selection. Critically, this invalidates part of the +41% that justified switching real trading on -- no test and no outlier check could have surfaced it, only real money could.
Solution : four changes, each measured before and after. (1) `finalized` is ~31 slots past confirmation, i.e. the 12-13s, and it is CONSENSUS, not the provider -- already on paid Helius, so no RPC can beat it. The commitment level became the caller's choice, `finalized` still the default so anything reading on-chain state keeps the old guarantee. Both trade legs now use `sent`, returning as soon as the chain accepts: a slot is 400ms, so the operator's 500ms target is unreachable any other way. (2) That is ONLY safe with `solana_late_bonding_shadow.reconcile_with_chain`, added in the same pass -- an open position holding nothing on-chain is cancelled (`buy_never_landed`), and a CLOSED position whose tokens are still held is REOPENED so the exit rule retries. The second case is exactly the FOMO stranding of the same night. A test fails if either leg skips confirmation while that reconciler is absent. (3) Preparation went 245ms -> 58ms: the SOL price now comes from a Jupiter SOL->USDC quote (25ms, and it IS the dollar price by construction) instead of CoinGecko (150ms, 61% of the whole budget), cached 60s following the pattern `pumpswap_ws` already used at 240s; decimals cached for the process lifetime since a mint's decimals are immutable. (4) Priority fee, the operator's catch: a flat 100_000 lamports had been INVENTED, which is 20.2% of a 0.10$ trade per round trip while `getRecentPrioritizationFees` showed the network's median, p75 AND p90 all at ZERO -- paying twenty percent to jump an empty queue. Now read from the chain (p75 of recent blocks), floored at 5_000 and capped at 20_000, measured at 2.4% per round trip, 88% less. Also fixed: polling for a confirmation every 400ms when a slot IS 400ms, so a confirmation landing at 410ms was only seen at 800ms -- now 100ms. STILL NOT VALIDATED: the fast path and the reconciler have never run against real money, real trading is stopped (delegate key moved aside, not deleted) and the shadow keeps collecting. Exit-price refresh measured at a 2696ms median, above the operator's 1000ms target -- the limit is the websocket's own notification rate, not processing, and two options remain open (widen what wakes the loop, or reprice locally from reserves already in memory). — `onchain/jupiter_swap_signer.py`, `onchain/jupiter_swap_simulation.py`, `solana_agent_wallet.py`, `solana_late_bonding_shadow.py`.

[CODE] Subject : two real-money bugs found within minutes of the first live run -- decimals ignored in the fill price, and Token-2022 accounts invisible to the inventory
Date : 2026.08.22 / Probleme : real trading was switched on and both defects surfaced immediately, neither caught by 11k tests. (1) Jupiter returns RAW units; dividing the dollar amount by them recorded a 6-decimal token at 1.6e-11 against a real 1.6e-5. The exit rule compares that entry to a market price in dollars-per-token, so the position showed roughly +100,000,000%, every profit rung fired at once, and the pocket bought at 0.10$ and sold 18 seconds later at 0.06$. In a wallet app this reads exactly like a drain. (2) `solana_rent_recovery.inventory()` scanned only the classic SPL Token program, but pump.fun mints are Token-2022 -- it reported ONE account while the wallet really held four, hiding 0.39$ of reclaimable deposits and the pocket's own open position. Found by the operator noticing his wallet app showed a token the audit did not.
Solution : (1) decimals read from the mint on BOTH legs (`token_decimals`), and an unreadable value REFUSES the trade rather than assuming the common 6 or 9 -- a wrong decimals silently rescales every price by a power of ten, which is the exact failure being fixed. (2) `TOKEN_PROGRAM_IDS` scans both programs, each account carries its owning `program_id`, and `build_close_instructions` addresses the close to THAT program -- a Token-2022 account closed against the classic program simply fails. Third fix, same session: `_real_trading_seams()` in the host process now falls back to SIMULATION when a kill-switch is engaged. `consider_candidate` treats a refused buy as "abort this entry", correct for one failed trade, but with custody paused it refused EVERY buy and the pocket silently stopped recording anything at all -- a paused system had stopped collecting the data the strategy is built on. Financial outcome of the whole episode: two round trips, wallet 28.62$ before and 28.63$ after, i.e. neutral. Lesson worth keeping beyond the fixes: a sanity check comparing the paid price against the market price before recording a position would have caught (1) in one second, and the 18-second round trip should have been read as a symptom rather than reported as an outcome. — `solana_agent_wallet.py`, `solana_rent_recovery.py`, `tests/test_solana_rent_recovery.py`.

[CODE] Subject : the pocket could buy for real but not SELL for real -- the missing half that made switching trading on unsafe
Date : 2026.08.22 / Probleme : `consider_candidate` had carried an `execute_fn` seam for real buys since 21/08, but `_apply_exit_check` had no counterpart. Exits only ever wrote to the table. Enabling real trading in that state would have had ARIA buy genuinely, then record "sold" at a stop while the tokens sat untouched in the wallet -- real capital stranded in collapsing memecoins, with the table reporting clean closures. Found by checking for the sell seam before switching anything on, not by hitting it in production.
Solution : `sell_fn` on `_apply_exit_check`, propagated through both call sites (polling sweep and event-driven handler) so the two never diverge, plus `solana_agent_wallet.execute_real_sell`/`_swap_out`/`token_balance`. Four decisions worth keeping: (1) the fraction passed is a share of the CURRENT holding, not of the original position -- the wallet's real balance already reflects earlier partial exits, so a share of the original would oversell on the second rung; (2) the quantity is read live from the chain rather than tracked, since any drift between the pocket's simulated `remaining_qty` and the real holding would compound silently across partial exits; (3) a refused or raising sell ABORTS the database write and leaves the position open, so the table can never claim an exit that did not happen, and the next pass retries; (4) selling is deliberately NOT behind `outgoing_pause`, unlike every buy -- the kill-switch exists to stop value LEAVING, while a sell converts a collapsing token back to SOL in the same wallet, and gating it would mean the emergency stop traps capital in exactly the positions the operator wanted out of. One real bug fixed in passing: `execute_real_buy` returned `tx_hash` while `consider_candidate` reads `filled.get("tx")`, silently dropping the only field that makes a row auditable on-chain. 7 end-to-end tests replay the genuine pocket code with only the money-touching seams faked, covering both directions of the stranding failure. Two measured findings, no code action taken: the fee load is light (3 transactions per round trip = 1.41% of a 0.10$ trade, 3.5% of the simulated PnL), but the peak of 59 SIMULTANEOUS positions seen across full history would need 17.22$ of capital+deposits against 15.01$ funded -- the pilot's real-balance check refuses cleanly rather than failing, so this costs missed entries, not money. The current epoch peaked at 3. — `solana_late_bonding_shadow.py`, `solana_agent_wallet.py`, `tests/test_solana_late_bonding_real_cycle.py`.

[CODE] Subject : the rent deposit -- not the trade size -- is what actually caps real Solana trading, and nothing ever reclaimed it
Date : 2026.08.22 / Probleme : holding a token on Solana requires opening an account for it, and opening that account locks 0.00204 SOL (0.19 $) of rent exemption. Nothing in the repo ever closed a token account, so the deposit was retired permanently on every distinct token ever bought. Measured against the real pocket this is structural, not cosmetic: the late-bonding pocket opened 755 DISTINCT tokens in 24 hours, and the funded wallet (0.1565 SOL) can hold only 71 accounts open at once -- saturation in ~2.3 hours. Critically, this is NOT solved by the fast rotation that makes the trading capital itself a non-issue (35% of closures happen under 2 minutes, mean hold 16.8 min): selling returns the 0.10 $ but LEAVES the account open and empty with its 0.19 $ still inside. Capital recycles, deposits do not. Jupiter's `wrapAndUnwrapSol: True` (already set in `jupiter_swap_simulation.build_swap_transaction`) closes the temporary wSOL account only -- it does nothing for the memecoin account, which is the one that matters here.
Solution : `solana_rent_recovery.py`. `inventory()` is read-only, gate-free, and classifies every token account into the four cases `CloseAccount`'s zero-balance requirement actually creates: `empty` (closes directly), `dust` (burn then close, both instructions in one transaction), `valued` (deliberately NOT touched -- selling is the pocket's decision, never a cleanup routine's), and `frozen` (freeze authority engaged: cannot transfer, burn, or close, the deposit is permanently lost and is surfaced as its own figure rather than folded into a "locked" total, since it doubles as a live scam-exposure metric). Instructions are built from raw `solders` primitives with the SPL Token program's consensus-frozen instruction indices (Burn=8, CloseAccount=9) rather than adding a dependency for two constants. Three deliberate refusals encoded as tests: an unknown price maps to `valued` and never to `dust` (a downed price feed must never authorise a burn); `valued`/`frozen` raise instead of returning an empty instruction list (a mis-filtering caller must hit an error, not a silent no-op reporting success); and the reclaimed deposit's destination is ALWAYS the owning wallet, structurally, never a parameter -- a "where should the money go" argument on a routine moving real value is the shape of a wallet-draining bug. Own gate `ARIA_SOLANA_RENT_RECOVERY_ENABLED`, OFF by default and deliberately distinct from the trade pilot's, so cleanup being enabled is never implied by trading being enabled. 28 offline tests; `inventory()` verified live against the real mainnet wallet (correctly classified the real USDC account as `valued`, refusing to burn it). NOT YET WIRED to any pocket or heartbeat caller, and no close has been executed with real funds -- that is a distinct step needing explicit operator validation. — `solana_rent_recovery.py`, `tests/test_solana_rent_recovery.py`.
