[CODE] Subject : Step 1 -- AllowanceModule ABI + live allowance reading, with the field order PROVEN experimentally
Date : 2026.08.17 / Probleme : step 1 of the plan (read a live allowance state) needs the module's ABI. Writing an ABI from memory is exactly the kind of shortcut that silently corrupts a financial guardrail -- and a first cross-check attempt was itself found WEAK mid-session and discarded: comparing `getTokenAllowance` against `allowances()` on an unconfigured Safe returns all zeros, which proves nothing about field ORDER (zero == zero in any order). A wrong field order would make `remaining` silently false.
Solution : ABI taken from the contract's VERIFIED source on Blockscout (Robinhood mainnet exposes the same CREATE2 address, `is_verified: true`, compiler v0.7.6), then each 4-byte selector recomputed and confirmed present in the bytecode actually deployed on testnet (a deliberately fake signature confirmed ABSENT in the same pass, proving the check discriminates). Field order then PROVEN experimentally via `eth_call` + `stateDiff` injecting a packed slot with five DISTINCT values (struct packs to exactly one slot, `allowances` is the first non-constant variable -> slot 0): all five returned in order. The same probe proved the contract's read-time reset (inject `spent=250` with a stale `lastResetMin` -> returns `spent=0`), which is what makes `remaining = amount - spent` trustworthy rather than stale. Zero on-chain writes (`stateDiff` is simulation-only). 19 dedicated tests, full suite green (10459). — `onchain/safe_robinhood_wallet.py`, `tests/test_safe_robinhood_wallet.py` (dfc57342)

[ETAT ACTUEL] Subject : Real scope today, and the three things that must be settled before any real capital
Date : 2026.08.17 / Probleme : snapshot to avoid a future session assuming this architecture is further along than it is, or missing the open blockers.
Solution : REAL SCOPE TODAY -- read-only, testnet/devnet only, zero private key, zero signing, and the modules are imported NOWHERE in production (verified three ways: no importer outside their own tests, not exported by `onchain/__init__.py`, no gate/env var triggering them). The embedded ABI contains ONLY `view` functions as a STRUCTURAL guardrail (web3 physically raises `ABIFunctionNotFound` on `setAllowance`/`executeAllowanceTransfer`), locked by `test_allowance_module_abi_is_read_only`. THREE OPEN POINTS before real capital: (1) AUDIT GAP -- Safe's official docs list an audit for AllowanceModule v0.1.0 (Oct 2020) ONLY; the deployed v0.1.1 has no audit listed. Mitigating fact, verified in the changelog: 0.1.1 = 0.1.0 + two BUG FIXES (broken EIP-712 typehash, and a `require(resetTimeMin > 0)` guarding a division-by-zero), i.e. strictly safer than the audited version, no new attack surface -- but this remains an operator decision, not a technical one. (2) NETWORK RESIDUAL -- the `read_*` helpers do not re-verify chain id on every call (would double RPC cost); harmless while read-only, but MUST become a hard pre-flight check before step 3 (signing). `read_module_identity()` reports the real chain id for a session that wants certainty. (3) ALLOWANCE REGIME -- `reset_time_min == 0` is a one-shot allowance that never refills (still reachable on v0.1.1: the `require` only fires when `resetBaseMin > 0`); a trading agent almost certainly wants the PERIODIC regime (a cap that refills), an operator design choice at step 2. NEXT STEPS unchanged: (2) Safe creation + module activation on testnet, (3) EIP-712 signing by the agent key, (4) full testnet cycle proving an over-limit spend is REJECTED on-chain, (5) only then a mainnet proposal. — `onchain/safe_robinhood_wallet.py`

[CODE] Subject : Step 2 -- full Safe+AllowanceModule cycle PROVEN in simulation, zero gas, zero key, zero on-chain write
Date : 2026.08.17 / Probleme : step 2 (Safe creation + module activation) is the first step that would write on-chain, and it was blocked on a hard operational dependency: the official testnet faucet (faucet.testnet.chain.robinhood.com) sits behind a Vercel challenge and is unreachable from the VPS, so no gas could be obtained autonomously. Waiting on the operator for a faucet would have stalled the whole chantier. Two design questions were also still open from step 1's ETAT ACTUEL: the allowance regime, and the un-enforced chain-id preflight.
Solution : rather than block, the entire cycle was proven by SIMULATION against the real deployed contracts (operator validated "simulate the whole cycle, up to proving the rejection"). New module `onchain/safe_robinhood_simulation.py`, deliberately SEPARATE from `safe_robinhood_wallet.py` so the latter's read-only ABI guardrail (`test_allowance_module_abi_is_read_only`) is not weakened -- the simulation module carries write-function ABIs but can only ever reach them through `eth_call`, locked by `test_simulation_module_never_sends_a_transaction` (AST-based, not a text scan: a text scan flags the module's own docstring, found live while writing it). FOUR things proven live rather than assumed: (1) the FULL Safe v1.4.1 stack is deployed on testnet 46630 -- proxy factory (3054 b), SafeL2 singleton (24421 b), fallback handler (5637 b), multisend -- step 1 had only ever checked the singleton, and without the FACTORY no Safe can be created at all, the real bloquant to rule out first; (2) this RPC accepts injected CODE in `eth_call` state overrides, not just injected storage as step 1 needed (verified with a 10-byte stub returning a sentinel); (3) Safe storage layout -- `threshold` at slot 4, proven by injecting the distinctive sentinel 7 and reading it back through the contract's own `getThreshold()`; (4) THE proof -- with a 100-unit one-shot allowance injected into the REAL AllowanceModule, amounts 50 and 100 clear the cap (stopping later at signature verification) while 101 and 150 revert on the module's own `newSpent > allowance.spent && newSpent <= allowance.amount` require. Testing the PASSING cases is what makes this a proof rather than an illusion: a contract that always reverted would look identical to a working guardrail if only the over-limit case had been checked. Boundary confirmed inclusive (100 passes, 101 rejected) and residual-envelope logic confirmed (with 50 of 100 already spent, 50 passes and 51 is rejected). Predicted Safe address for owner-A1/nonce-0: `0x4b6A95c869B680c5e5B333802B6F30Cf7a592c73` (no code at it -- nothing was deployed). OPEN POINT (2) OF STEP 1 NOW CLOSED: a fail-closed chain-id preflight runs on every public entry point (an RPC repointed at mainnet 4663 raises instead of simulating against real balances), asserted per-entry-point in tests. OPEN POINT (3) DECIDED BY THE OPERATOR (17/08): one-shot regime (`reset_time_min=0`, the cap never refills by itself, re-arming is a human action) for the pilot, chosen over periodic so a compromised agent's maximum loss is the envelope itself rather than the envelope every period; periodic stays reachable by passing a non-zero value, deliberately not the default, locked by `test_one_shot_is_the_default_regime`. Operator also confirmed the same day that the target architecture is smart wallets, not EOAs -- consistent with this Safe-based design (the EOA is only ever a signing key; the capital and the enforced bounds live in the contract). 19 dedicated tests. STILL OUT OF SCOPE: no real Safe exists, no key, no signing, no mainnet -- real execution needs testnet gas from the operator, and open point (1) (v0.1.1 audit gap) remains an operator decision before any real capital. — `onchain/safe_robinhood_simulation.py`, `tests/test_safe_robinhood_simulation.py` (pending commit)
