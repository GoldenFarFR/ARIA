[ETAT ACTUEL] Subject  : Item #116 -- probable root cause found (not 100% certain), structural fragility documented, no code change (research task)
Date : 2026.07.26 / Problem : follow-up research task on the entry above -- retrace exactly how a Virtuals catalog ID reached `_resolve_model` despite `llm_economy._spark_model_for_depth`'s existing guard. Re-audited ALL 41 real call sites of `chat_with_context` across the codebase (not just a sample) -- only `brain.py` (4 sites) passes an explicit `model=` (via `budget.model_override`), which always flows through `llm_economy.resolve_budget()` -> `_spark_model_for_depth()`, so the guard IS on that path for every case tested with today's live config (`LLM_PROVIDER=grok`, `ARIA_LLM_MODEL_DEVELOP=anthropic-claude-opus-4-8` in the real container env -- re-verified live, guard correctly returns `None`).
Solution : the guard compares `raw` (from `settings.aria_llm_model_develop`, a Pydantic field read from the container's real `.env` at boot) against `_virtuals_catalog_default(depth)` (`spark_config.DEFAULT_MODEL_DEVELOP`, computed at MODULE IMPORT from `ecosystem_registry.yaml`'s `defaults.ARIA_LLM_MODEL_DEVELOP` via `registry_defaults()`) -- TWO INDEPENDENT SOURCES OF TRUTH for "what is today's Virtuals catalog default", each snapshotted once at process start from a DIFFERENT origin (real `.env` vs. committed YAML). `git log -p` on `ecosystem_registry.yaml` confirms `ARIA_LLM_MODEL_DEVELOP` genuinely flipped value several times across past sessions (`x-ai-grok-4-3` <-> `anthropic-claude-opus-4-8` <-> empty) -- if the real `.env` and the committed YAML were ever out of step for even one deploy cycle (one updated, the other not yet redeployed), the exact-match comparison silently fails and a stale Virtuals ID sails through uncaught. A SEPARATE, independently-found instance of the same class of divergence exists TODAY for BRIEF: the registry's active `chiron` profile sets `aria_llm_model_brief: x-ai-grok-4-3`, but `vanguard/backend/app/config.py`'s Pydantic default is hardcoded `"deepseek-deepseek-v4-flash"` (the `sport` profile's value) -- harmless today only because that particular ID happens to still be a valid Virtuals catalog entry, not because the divergence was caught. Not fixed here (root cause is a structural "two SSOTs that can silently drift" issue, a real fix means unifying how `Settings.aria_llm_model_*` and `spark_config.DEFAULT_MODEL_*` are sourced -- out of scope for this research pass, flagged as backlog #118 below). The defensive guard already shipped in `_resolve_model` (entry above) remains the real safety net regardless of which SSOT drifted -- no further code change made, this entry documents the investigation's findings honestly rather than closing with a guessed fix.
