[ETAT ACTUEL] Subject : "throughput calibrated to 90% of real capacity, never guessed" doctrine -- the 3 founding incidents that carved it into CLAUDE.md as a permanent norm
Date : 2026.07.19→21 / Problem : three real incidents in 3 days established that an unverified rate-limit figure or uncoordinated throughput between multiple clients of the same provider is as dangerous as a real bug. (1) 19/07: a "100 req/min" GeckoTerminal figure never verified under real sustained conditions, confused with an unrelated CoinGecko tier, produced ~79% HTTP 429 failure for over an hour. (2) 21/07: two independent GeckoTerminal clients (aria-core and vanguard/backend) each individually well-calibrated but never coordinated with each other, combined throughput exceeding the real ceiling, 55% sustained failure. (3) later confirmed twice more: a documented limit can itself be false or misleading -- GoPlus's official doc announces 100-150 req/min but a real burst test shows a block as early as the 11th request (~11s recovery, real sustained throughput closer to ~55/min); Tavily announces 100/min at "Development" tier vs 1000/min at "Production", the two easy to confuse without checking which applies to the actually-configured key.
Solution : the norm now carved in CLAUDE.md ("Permanent norms") derives directly from these 3 incidents -- every external API client throttle must be calibrated to ~90% of a REAL verified sustained rate (official doc OR empirical burst test, never assumed/recalled from memory), sourced in a comment next to the throttle constant; several clients of the SAME provider must share ONE coordination point (`aria_core.services.geckoterminal.wait_for_shared_rate_limit` as the reference pattern), never independent throttles that silently add up. A limit documented nowhere: keep reactive backoff (retry on 429/5xx) WITHOUT a numeric proactive throttle, explicitly documented as "unknown capacity" rather than fabricated precision. Calibration inventory (services covered, sourced limit, current/target throttle): `docs/api-rate-limit-calibration.md`. — no single code file, this is the doctrine's own origin story; see `docs/api-rate-limit-calibration.md` for the live per-service state.

[CODE] Subject : #302 -- resource_budget.py built, Dune migrated first (simplest provider: fixed 1-execution cost, no per-call formula)
Date : 2026.08.13 / Problem : Devil's Advocate flagged 7 near-duplicate budget/quota guard modules (real total confirmed 10 -- CoinGecko/Mobula/Dune had inline tracking, no dedicated module, see comparative mapping this session produced). Operator go-ahead given for the consolidation. A naive single `check()`/`record()` API across all 10 would break real production behavior -- 10 concrete divergences found (append-only log+SUM vs SingleRowStore state machine, `can_spend()` positive=allowed vs `is_suspended()` positive=refused, Firecrawl runs TWO deliberately-stacked guards, only 1/10 documents fail-open, etc.) -- full mapping kept in this file's own history (see the comparative-mapping subagent report referenced in the Devil's Advocate archived report, `/opt/aria-data/architect-reports/archived/b5ed70d252ebd7181e229ea9aac6c90044490fd8.md`).
Solution : scoped this consolidation to the 6 same-shape "log-based" mechanisms only (CoinGecko, Mobula, Dune, Blockscout, Firecrawl-budget, Tavily-budget -- suspend-only, no Telegram alert, one calendar window, no distant balance read) -- the 4 SingleRowStore state machines (GoPlus/CMC/Firecrawl-overspend/TwitterAPI.io) stay separate modules, their semantics are too different to share an API without silently changing behavior. New `services/resource_budget.py`: one shared `resource_budget_log` table (provider/caller/query/cost/recorded_at), `spent_in_window()`/`can_spend()`/`record_spend()`, `window`/`cap` always passed in EXPLICITLY by the calling module rather than a duplicated internal registry (a registry in two places is exactly the drift this consolidation removes) -- `can_spend()` checks `spent + cost <= cap` (stricter than some pre-migration `spent >= cap` checks that ignored the size of the call about to be made, a real latent gap for a provider with variable per-call cost; for Dune specifically, every call costs exactly 1, so this is an EXACT behavioral match, not a change). Lazy idempotent legacy-table migration (`_migrate_legacy_log_if_needed`): on first use per provider, copies the provider's pre-existing log table into the shared ledger IF the shared ledger has no row for that provider yet -- never resets a mid-month counter to zero (would silently blow through the provider's REAL external quota), never double-copies. `dune.py` migrated first (`_executions_this_month`/`_record_execution`/`_monthly_cap_reached` now thin facades delegating to `resource_budget`, function names/signatures unchanged, zero consumer touched, `_MONTHLY_EXECUTION_CAP` still owned by `dune.py` and passed to `can_spend(cap=...)` explicitly so an existing test's `monkeypatch.setattr(dune, "_MONTHLY_EXECUTION_CAP", ...)` still works). CoinGecko/Mobula/Blockscout/Firecrawl-budget/Tavily-budget migrations intentionally NOT done in this commit -- next sessions, one provider per commit, same facade pattern, per the original 3-step transition plan (extraction -> migrate one at a time -> remove facades once all consumers are direct).
`services/resource_budget.py` (new) / `services/dune.py` (3 functions now facades) / `tests/test_resource_budget.py` (new, 14 tests: window math, cap enforcement including the stricter-than-before edge case, idempotent legacy migration with a real pre-populated legacy table, no-legacy-table and unregistered-provider no-ops) / `tests/test_dune_client.py` (unchanged behavior, all 121 tests still pass unmodified) -- targeted suite green (135 passed), full suite run before next commit.

[CODE] Subject : `geckoterminal_outage_suspension.py` -- 5th SingleRowStore backoff mechanism, GeckoTerminal had none before this
Date : 2026.08.17 / Problem : diagnosing a Devil's Advocate report on the new Solana/Robinhood pump shadow (report a8e125b9) led to finding a MUCH larger, pre-existing live incident: 605 consecutive HTTP 429 from GeckoTerminal over 9h40+ with zero gap (00:00-09:42 UTC), confirmed via a live probe to be an account/IP-level block (a bare, UNAUTHENTICATED call to the most basic endpoint (`/networks`) also returned 429 -- not a per-key quota, not a per-endpoint limit). GeckoTerminal was the only major provider in this file's own consolidation with ZERO circuit-breaker of any kind -- its adaptive throttle (`GeckoTerminalClient._record_rate_limit`) caps its own backoff at 3x the floor (12s) and NEVER goes further, so under a sustained block it just keeps retrying forever at that fixed worst-case pace, wasting hundreds of doomed requests over many hours instead of ever giving the account real time to recover.
Solution : `geckoterminal_outage_suspension.py` (new), same `SingleRowStore` exponential-backoff doctrine as `goplus_quota_suspension.py` (5 consecutive real 429s to arm -- higher than GoPlus's 3, since GeckoTerminal carries far more legitimate traffic and its own adaptive throttle already absorbs an isolated burst; 15min initial window, doubles on each post-expiry probe failure, capped at 24h -- deliberately far below GoPlus's 48h ceiling since GeckoTerminal is load-bearing for the whole system, better to keep probing more often than black it out for two full days on a wrong guess about the real cause). Wired into `GeckoTerminalClient._get_json` (the one chokepoint every call already funnels through): `is_suspended()` checked FIRST, before any network attempt (fail-closed); `record_rate_limit_failure()`/`record_success()` called alongside the existing per-instance throttle's own `_record_rate_limit()`/`_record_success()`, zero coupling between the two mechanisms. The REAL root cause (monthly quota exhausted vs a temporary Cloudflare-level burst block) was NOT conclusively identified this session -- operator asked to check the CoinGecko dashboard (`coingecko.com/en/developers/dashboard`) directly; the exponential backoff self-calibrates either way without needing to know in advance. 6 new tests mirror `test_goplus_quota_suspension.py`'s exact pattern; `test_geckoterminal_client.py` (65 tests) and `test_coherence.py` (157 tests) both green after the `_get_json` wiring; full repo suite run before commit.
`geckoterminal_outage_suspension.py` (new) / `services/geckoterminal.py` (`_get_json` wiring) / `tests/test_geckoterminal_outage_suspension.py` (new, 6 tests).
