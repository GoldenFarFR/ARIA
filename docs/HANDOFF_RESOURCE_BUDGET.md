[ETAT ACTUEL] Subject : "throughput calibrated to 90% of real capacity, never guessed" doctrine -- the 3 founding incidents that carved it into CLAUDE.md as a permanent norm
Date : 2026.07.19→21 / Problem : three real incidents in 3 days established that an unverified rate-limit figure or uncoordinated throughput between multiple clients of the same provider is as dangerous as a real bug. (1) 19/07: a "100 req/min" GeckoTerminal figure never verified under real sustained conditions, confused with an unrelated CoinGecko tier, produced ~79% HTTP 429 failure for over an hour. (2) 21/07: two independent GeckoTerminal clients (aria-core and vanguard/backend) each individually well-calibrated but never coordinated with each other, combined throughput exceeding the real ceiling, 55% sustained failure. (3) later confirmed twice more: a documented limit can itself be false or misleading -- GoPlus's official doc announces 100-150 req/min but a real burst test shows a block as early as the 11th request (~11s recovery, real sustained throughput closer to ~55/min); Tavily announces 100/min at "Development" tier vs 1000/min at "Production", the two easy to confuse without checking which applies to the actually-configured key.
Solution : the norm now carved in CLAUDE.md ("Permanent norms") derives directly from these 3 incidents -- every external API client throttle must be calibrated to ~90% of a REAL verified sustained rate (official doc OR empirical burst test, never assumed/recalled from memory), sourced in a comment next to the throttle constant; several clients of the SAME provider must share ONE coordination point (`aria_core.services.geckoterminal.wait_for_shared_rate_limit` as the reference pattern), never independent throttles that silently add up. A limit documented nowhere: keep reactive backoff (retry on 429/5xx) WITHOUT a numeric proactive throttle, explicitly documented as "unknown capacity" rather than fabricated precision. Calibration inventory (services covered, sourced limit, current/target throttle): `docs/api-rate-limit-calibration.md`. — no single code file, this is the doctrine's own origin story; see `docs/api-rate-limit-calibration.md` for the live per-service state.
