[CODE] Subject : wallet_copy_shadow_dynamic_candidates registry -- full lifecycle (absolute cap + worst-first eviction + TTL + dormancy purge) (#172)
Date : 2026.08.15 / Problem : the dynamic registry (#146, wallets sourced off the real leaderboard) had NO lifecycle at all -- once added, a wallet stayed tracked (sequential Blockscout scan every cycle) forever, with no way back out even once dormant or no longer competitive. #147/#151's sourcing work is actively growing the leaderboard's population (exactly what #146's own comment was waiting for) -- unbounded growth here would only ever slow `run_scan_cycle` down further, never self-correct. The 8 hand-picked `TRACKED_WALLETS` stay deliberately outside this mechanism -- permanent by design.
Solution : `MAX_DYNAMIC_CANDIDATES=20` (absolute cap) + `DYNAMIC_CANDIDATE_MAX_AGE_DAYS=90` (TTL -- a percentile at discovery is a snapshot, not a standing guarantee). `discover_leaderboard_candidates()` now applies the same worst-first eviction as `goplus_watchlist.add_or_touch`: registry full -> a new candidate only earns a slot if it beats the current worst tracked percentile (a tie never evicts). New `evict_stale_dynamic_candidates()` -- purges (1) expired TTL, (2) real dormancy (a cursor exists -- at least one scan has run -- and its last on-chain transfer exceeds `INACTIVITY_THRESHOLD_DAYS`, the same threshold `summary()` already used for the label, now also acted on here); a candidate with NO cursor yet (never scanned) is never evicted as dormant -- "not scanned yet" != "went quiet". Wired into `heartbeat.py` right after `discover_leaderboard_candidates()`, same `ARIA_WALLET_COPY_SHADOW_DYNAMIC_ENABLED` sub-gate. Never touches historical position/cursor rows (kept as-is, the wallet simply stops being scanned/reported once evicted) nor the 8 static wallets. 10 new tests (`test_wallet_copy_shadow.py`): worst-first eviction when full, skip when the newcomer doesn't beat the worst, TTL purge, dormancy purge, never evicts an unscanned candidate, never purges static wallets, clean degradation without a table. Targeted suite green (192 passed) + full collect-only clean (10202 tests). — `wallet_copy_shadow.py`, `heartbeat.py`, `tests/test_wallet_copy_shadow.py`.

[DEPLOYE] Sujet : dust/spam-token price artifact fixed -- P&L stats recomputed clean
Date : 2026.08.10 / Problem : auditing live data found 8 open shadow positions (across 6 of the 8 tracked wallets) with absurd latent P&L ratios up to +8.6e15% -- root cause: `scan_wallet()` treats every non-quote ERC-20 transfer IN as a "buy" with no way to tell a real swap from a dust/spam airdrop. `_current_price_usd()` then trusted whatever DexScreener returned for that token's pool, even a near-empty one (real case: "(RNDR)" at a $1.45-liquidity pool, price 4.268e-24 -- not a real market). Several tokens (XST, AC0R, DOS, Doom) hit the exact same artifact price across MULTIPLE tracked wallets simultaneously, consistent with a mass dust-airdrop/phishing pattern, not independent trades.
Solution : `_MIN_POOL_LIQUIDITY_USD_FOR_PRICE = 1,000$` floor added to `_current_price_usd()` -- a pool below it degrades to `None` (same honest fallback as no pool found at all), preventing future dust prices from being captured on open OR close. `_PLAUSIBLE_PRICE_RATIO_BOUNDS = (0.001, 1000.0)` mechanical safety net added in `summary()` -- excludes any entry/exit or entry/mark ratio outside this range from the aggregate (this pipeline's largest real documented pumps are on the order of x10-x50, never anywhere near x1000), protecting against both the 6 already-recorded artifacts and any future edge case the liquidity floor alone doesn't catch. Not a retroactive DB cleanup (the poisoned rows stay in the table for traceability) -- `summary()`'s filter is what keeps them out of the reported numbers going forward. — `wallet_copy_shadow.py`, `test_wallet_copy_shadow.py` (3 new tests: liquidity floor rejects/accepts, plausibility filter excludes an artifact while keeping a real x3 gain).

**Clean numbers, recomputed same day** (8 tracked wallets confirmed -- an earlier count of "10" cited in conversation this session was a miscounted `grep`, corrected here): CLOSED (realized) P&L is flat-to-slightly-negative on every wallet with any closed trades (gmgn_0x8d_b74d -$868, gmgn_antpositions -$27, others $0/no losses recorded yet) -- but UNREALIZED (still-open) latent P&L is strongly positive on several: gmgn_0x8d_b74d +$8,168 (on top of its own -$868 realized loss), gmgn_antpositions +$4,487, gmgn_alexwong +$1,001, thokani +$1,062. Consistent with the pattern already noted 2026.08.08 in this same file (swing pocket: 0% closed win rate but a real +35.7% latent position) and with the operator's own live hypothesis this session ("peut-etre que pour etre performant c'est un winrate vers 35% mais plus de benefice avec des positions qui laissent tenir") -- these wallets' realized track record looks unremarkable/negative in isolation, their real edge (if any) is in what they let run, not yet closed at observation time. Not a validated conclusion (unrealized can still reverse before a real close) -- a signal to keep watching, not to act on.
