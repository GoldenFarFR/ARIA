[CODE] Subject  : Mobile chat always answered in English regardless of the operator's own language (Item #201)
Date : 2026.07.30 / Problem : real production bug caught by the operator's own end-to-end test of the just-deployed Phase 1/2 (login + chat) — he asked ARIA a question in French from the Android app and got an English answer back ("0 open positions across all pockets. Paper-trading capital stands at 1,000,000 $ with zero P&L."). Traced to `AriaBrain.process(user_message, lang=LANG_EN, ...)` -- English is the function's own default, and `/aria/ops/chat` never passed `lang` at all. Never caught before because Telegram auto-translates the display for the operator (documented elsewhere in this file); the Android app translates nothing, so this is the first surface where the gap was actually visible. Not cosmetic: the operator does not read English (CLAUDE.md, operator profile) -- a fallback channel meant to work when Telegram is down answering in a language its only user can't read is a functional failure of the channel's entire purpose.
Solution : `ChatBody.lang: Literal["fr", "en"] = LANG_FR` (French default, deliberately diverging from `AriaBrain.process()`'s own English default -- commented in place so a future session doesn't "fix" the divergence back). Passed through explicitly to `aria_brain.process(..., lang=body.lang, ...)`. Optional field -> the already-installed APK gets French with zero rebuild; a future client can still pick English.
`vanguard/backend/app/api/routes/operator_mobile.py` -- 3 tests (`test_operator_mobile_routes.py`: absent field defaults to "fr", explicit "en" honored, unsupported locale -> 422 without ever reaching the brain). Full suite green (aria-core 8496 passed/17 skipped, backend 208 passed), `test_coherence.py` green.

[CODE] Subject  : Phase 3 -- kill-switch REST (/stop, /resume, /history), TOTP anti-replay (Item #201)
Date : 2026.07.30 / Problem : the mobile fallback channel had login/session/chat (Phases 1-2) but no way to arm or lift the kill-switch from the app -- the whole point of a channel meant to work when Telegram is down. The plan's core requirement: the sliding session alone (fine for chat) is far too permissive for the one control that can really hurt.
Solution : `POST /aria/ops/stop` / `POST /aria/ops/resume` now require BOTH the mobile session AND a fresh TOTP code on every call (`_require_fresh_totp`), checked via the account's own `verify_totp` then consumed by a new anti-replay claim -- never cached, never derived from the session. Anti-replay is a dedicated table (`operator_used_totp_codes`, new `app/auth/operator_totp_replay.py`) with `UNIQUE(account_id, totp_code)`: the DB itself rejects a second insert of the same pair, so two concurrent calls with the same code can never both pass a check-then-mark race (proven by a test firing 8 concurrent claims of one code -- exactly 1 winner). A dedicated throttle (`KILL_SWITCH_MAX_ATTEMPTS=15`/5min, `check_rate_limit`) bounds brute-forcing a stolen session's TOTP guesses, always self-releasing -- the plan forbids a hard lock on a fallback channel. The legacy server-to-server path (`X-Admin-Secret`/`X-Admin-Totp`, a different `ADMIN_TOTP_SECRET`) is exempt from this second factor -- it already presented its own TOTP to `is_operator_request`, an assumed difference in level (serves scripts, not a human app reusing one code repeatedly), documented in the plan. Both routes are idempotent (arming an already-armed pause, or resuming an already-resumed one, returns `changed=false` and logs nothing -- a network retry must never look like a failure or pollute the audit trail). `record_incident` failures never block the real action (audit is observability, never a gate) -- proven by a test that makes the log call raise and confirms the pause still armed. `GET /aria/ops/history?limit=N` reuses `kill_incident_log.list_incidents`, capped server-side (`HISTORY_MAX_LIMIT=100`) regardless of what the client asks for.
Real edge case found and handled deliberately: a corrupted `pause_state.json` reads as `paused=False` (fail-open on the read) but freezes spending fail-closed (`outgoing_pause.money_block_reason`) -- treating that as "already resumed" would leave the operator with no way to unfreeze money from this channel. `/resume` now also repairs an unreadable state (writes a clean one), and that IS logged as a real change.
`vanguard/backend/app/auth/operator_totp_replay.py` (new), `operator_mobile.py` -- 27 new tests across `test_operator_totp_replay.py` (new) and `test_operator_mobile_routes.py`, +1 structural invariant in `test_coherence.py` (the only one of these actually wired to CI -- see residual below). Full suite green (aria-core 8496 passed/17 skipped, backend 208 passed), `test_coherence.py` green. Not yet deployed -- reviewed and committed by the command session, never blind-trusted from the subagent's own report.
