[CODE] Subject : x402 payment mechanism hardened -- 4 real gaps closed (race condition, rolling window, per-transaction cap, provider allowlist), not yet deployed
Date : 2026.08.03 / Problem : operator asked Claude Fable 5 for a security second opinion on x402 payments, then had a 2-agent workflow verify each claim against the real code. Confirmed real: (1) `can_spend()`/`record_spend()` were a check-then-act pair with no transaction/lock between them -- two concurrent callers (the actual incident: two parallel workflow sub-agents, two separate processes) could both read "budget still free" before either recorded a spend, exceeding the cap; (2) `week_start()` was a CALENDAR week (Monday 00:00 UTC) -- up to ~2x the cap could be spent in a few minutes around the reset; (3) no hard cap on a SINGLE transaction, distinct from the weekly cap -- a provider's 402 challenge could request up to the entire remaining budget; (4) only the NETWORK was checked against an allowlist, never the provider's own domain -- any URL could be called.
Solution : `week_start()` now returns a rolling 7-day window (`now - 7 days`), not a calendar boundary -- one test renamed to match, no other regression (the old test's 8-day-old spend still falls outside a 7-day window). New `MAX_TRANSACTION_USD = 0.10` (~3.3x the most expensive real provider today, Quick Intel at $0.03) checked before the weekly cap. New `_ALLOWED_PROVIDER_DOMAINS` (derived from `urlparse(url).hostname`, zero change to any of the 7 existing callers' own call signature) checked BEFORE even the unpaid 402 challenge request, not just before payment. Race condition fixed with a genuinely atomic `try_reserve()`/`settle()` pair (SQLite `BEGIN IMMEDIATE`, a file-level lock that protects across separate processes, unlike an in-process `asyncio.Lock` which would NOT have prevented the real incident) replacing the old `can_spend()`/`record_spend()` sequence in `fetch_paid_resource` -- a reservation is `'pending'` (counts against the budget) until `settle()` resolves it to `'ok'`/`'failed'`; a crashed reservation ages out after `PENDING_TIMEOUT_MINUTES=5` rather than freezing the budget forever. Verified live with a real concurrency test (`asyncio.gather` on two $3 reservations against a $5 cap): exactly one reservation succeeds, never both.
`x402_executor.py`/`x402_budget.py` -- new regression tests in `test_x402_executor.py`/`test_x402_budget.py`, full suite green, `test_coherence.py` green. Same-day companion fix: `momentum_entry._check_holder_concentration` (the guardrail this whole review was triggered by, per Fable 5's own top risk -- "a 3-cent provider influencing a much bigger trade") now fails CLOSED instead of open when holder data is unavailable, on both the real pilot and paper trading -- see the dedicated commit message for detail, not duplicated here.
