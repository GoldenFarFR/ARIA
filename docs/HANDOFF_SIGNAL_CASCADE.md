[CODE] Sujet  : colonne GitHub, étages 1+2 (COLLECT + FILTRE QUANTITATIF)
Date : 2026.08.08 / Probleme : le cas aeon a prouvé que `github_substance.py` (score de substance réelle du code, déjà existant) ne tourne QUE sur un candidat qui a déjà franchi le filtre technique BUY via `vc_analysis.py` — un fork frais avec un vrai développement mais sans encore de momentum de prix (exactement le cas aeon à son ATL) est invisible tant qu'il n'a pas déjà bougé.
Solution : nouveau `signal_cascade_github.py`. Étage 1 COLLECT : `enqueue_candidate(contract, chain, project_links)` câblé DIRECTEMENT dans `momentum_entry.evaluate_hard_gates`, juste après la résolution du meilleur pair DexScreener — AVANT tout filtre de liquidité/technique/sécurité, donc pour absolument tout candidat scanné (des ~100/cycle), pas seulement ceux qui achètent. Coût réseau nul (un simple `INSERT OR IGNORE`, jamais un doublon, jamais de réécriture d'un repo déjà connu). Étage 2 FILTRE QUANTITATIF : nouvelle tâche heartbeat `github_signal_cascade_cycle` (15min, 1 repo par passage — même doctrine de débit que `goplus_watchlist_cycle`), réévalue au plus 1x/24j (`REEVALUATION_TTL_DAYS`) via `github_substance.gather_github_substance_facts`/`judge_github_substance` INCHANGÉS (aucun nouveau seuil inventé — le seuil "positive" déjà calibré à 70/100 reste l'unique critère). Ajout : détection d'ACCÉLÉRATION (`previous_signal` faible/inconnu → nouveau signal positif) — le vrai signal recherché est un projet qui DÉMARRE, pas un projet mature qui reste positif indéfiniment. `list_stage2_positive()` expose ce que l'étage 2 laisse passer — c'est la graine (seam) que la future table de convergence (étage 3, pas construit ici) consommera. Gate dédié `ARIA_GITHUB_SIGNAL_CASCADE_ENABLED` (OFF par défaut), pas de double-gate avec le paper trading (pipeline de recherche indépendant, même si nourri par le scan momentum).
`signal_cascade_github.py`/`momentum_entry.py`/`heartbeat.py`/`tests/test_signal_cascade_github.py` — 10 nouveaux tests (enqueue idempotent, sans lien GitHub → rien, jamais de levée d'exception même DB cassée, refresh respecte le TTL, détection d'accélération correcte dans les deux sens, filtre stage 2 exclut weak/unknown). Déployé (commit `3cfc7240`, gate activé le jour même).

[DEPLOYE] Sujet : étages 3 (CONVERGENCE) + 4 (FILE PERSISTANTE), première colonne (GitHub) câblée bout en bout
Date : 2026.08.09 / Probleme : l'étage 2 GitHub laissait passer des signaux "positive"/"accelerating" sans nulle part où ils s'accumulent — pas de vue partagée entre colonnes (une seule pour l'instant, mais la table doit déjà être prête pour Farcaster/web/X), pas de file que Claude Code puisse effectivement consulter en reprenant une session (design opérateur : "jamais une notification volatile").
Solution : nouveau `signal_cascade_convergence.py`. Étage 3 : `record_source_signal(contract, chain, source, signal, ...)` — un seul point d'entrée que TOUTE colonne source appellera de la même façon (aujourd'hui : `signal_cascade_github.run_refresh_cycle` seul appelant) ; table `signal_cascade_convergence` une ligne par (contract, chain, source), le score de convergence = COUNT des sources en 'positive' sur ce token. Étage 4 : `signal_cascade_triage_queue`, une entrée par (contract, chain), jamais dupliquée. `record_triage_decision` EXIGE un raisonnement non vide (design opérateur : "capturer le POURQUOI, jamais juste le verdict" — prépare le test de falsifiabilité futur, comparer les rendements des picks validés vs rejetés, pas construit ici). **Bug réel trouvé et corrigé pendant la construction (pas en prod, jamais déployé cassé)** : le `convergence_count` stocké se figeait à sa valeur de première insertion — une 2e source confirmant plus tard n'était jamais reflétée. Corrigé : une ligne encore `pending` est mise à jour en place (jamais dupliquée) ; une ligne déjà `validated`/`rejected` n'est JAMAIS rouverte par un signal ultérieur (décision humaine irréversible par construction). Étage 4 "lu par Claude Code au démarrage de session" mécanisé via un nouveau hook `SessionStart` (`signal-cascade-queue-reminder.sh`, lecture seule, silencieux si file vide ou DB absente) — sans lui la file existerait mais personne n'irait jamais la consulter.
