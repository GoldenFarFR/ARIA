Solution : nouveau `signal_cascade_github.py`. Étage 1 COLLECT : `enqueue_candidate(contract, chain, project_links)` câblé DIRECTEMENT dans `momentum_entry.evaluate_hard_gates`, juste après la résolution du meilleur pair DexScreener — AVANT tout filtre de liquidité/technique/sécurité, donc pour absolument tout candidat scanné (des ~100/cycle), pas seulement ceux qui achètent. Étage 2 FILTRE QUANTITATIF : nouvelle tâche heartbeat `github_signal_cascade_cycle` (15min, 1 repo par passage — même doctrine de débit que `goplus_watchlist_cycle`), réévalue au plus 1x/24j (`REEVALUATION_TTL_DAYS`) via `github_substance.gather_github_substance_facts`/`judge_github_substance` INCHANGÉS (aucun nouveau seuil inventé — le seuil "positive" déjà calibré à 70/100 reste l'unique critère). Ajout : détection d'ACCÉLÉRATION (`previous_signal` faible/inconnu → nouveau signal positif) — le vrai signal recherché est un projet qui DÉMARRE, pas un projet mature qui reste positif indéfiniment. `list_stage2_positive()` expose ce que l'étage 2 laisse passer — c'est la graine (seam) que la future table de convergence (étage 3, pas construit ici) consommera. Gate dédié `ARIA_GITHUB_SIGNAL_CASCADE_ENABLED` (OFF par défaut), pas de double-gate avec le paper trading (pipeline de recherche indépendant, même si nourri par le scan momentum).
`signal_cascade_github.py`/`momentum_entry.py`/`heartbeat.py`/`tests/test_signal_cascade_github.py` — 10 nouveaux tests (enqueue idempotent, sans lien GitHub → rien, jamais de levée d'exception même DB cassée, refresh respecte le TTL, détection d'accélération correcte dans les deux sens, filtre stage 2 exclut weak/unknown).
