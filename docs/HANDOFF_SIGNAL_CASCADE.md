Date : 2026.08.08 / Probleme : le cas aeon a prouvé que `github_substance.py` (score de substance réelle du code, déjà existant) ne tourne QUE sur un candidat qui a déjà franchi le filtre technique BUY via `vc_analysis.py` — un fork frais avec un vrai développement mais sans encore de momentum de prix (exactement le cas aeon à son ATL) est invisible tant qu'il n'a pas déjà bougé.
Solution : nouveau `signal_cascade_github.py`. Étage 1 COLLECT : `enqueue_candidate(contract, chain, project_links)` câblé DIRECTEMENT dans `momentum_entry.evaluate_hard_gates`, juste après la résolution du meilleur pair DexScreener — AVANT tout filtre de liquidité/technique/sécurité, donc pour absolument tout candidat scanné (des ~100/cycle), pas seulement ceux qui achètent. Coût réseau nul (un simple `INSERT OR IGNORE`, jamais un doublon, jamais de réécriture d'un repo déjà connu). Étage 2 FILTRE QUANTITATIF : nouvelle tâche heartbeat `github_signal_cascade_cycle` (15min, 1 repo par passage — même doctrine de débit que `goplus_watchlist_cycle`), réévalue au plus 1x/24j (`REEVALUATION_TTL_DAYS`) via `github_substance.gather_github_substance_facts`/`judge_github_substance` INCHANGÉS (aucun nouveau seuil inventé — le seuil "positive" déjà calibré à 70/100 reste l'unique critère). Gate dédié `ARIA_GITHUB_SIGNAL_CASCADE_ENABLED` (OFF par défaut), pas de double-gate avec le paper trading (pipeline de recherche indépendant, même si nourri par le scan momentum).
`signal_cascade_github.py`/`momentum_entry.py`/`heartbeat.py`/`tests/test_signal_cascade_github.py` — 10 nouveaux tests (enqueue idempotent, sans lien GitHub → rien, jamais de levée d'exception même DB cassée, refresh respecte le TTL, détection d'accélération correcte dans les deux sens, filtre stage 2 exclut weak/unknown). [DEPLOYE] Sujet : test de falsifiabilité -- rendement réel des picks validés vs rejetés par Claude

Solution : extension de `signal_cascade_convergence.py` (pas un nouveau fichier -- le stage 4 possède déjà la table de décisions, le test de falsifiabilité lui appartient naturellement). `record_triage_decision` capture désormais le prix du token AU MOMENT de la décision (`price_at_decision`, best-effort -- un échec de lookup n'empêche jamais d'enregistrer la décision elle-même). `refresh_forward_prices()` remplit paresseusement `price_after_24h`/`price_after_7d` -- même doctrine que `narrative_signal_shadow.py` : pas de poller dédié, le rendement est capturé la première fois qu'on regarde après la fenêtre écoulée, jamais une ligne déjà remplie n'est réécrite. `falsifiability_report()` compare le rendement moyen des VALIDÉS vs REJETÉS sur chaque fenêtre (24h/7j), avec un verdict textuel HONNÊTE : jamais de conclusion en dessous de `_MIN_SAMPLES_PER_SIDE=5` échantillons résolus de CHAQUE côté ("pas assez de données") -- le mécanisme est prêt mais aucune décision de triage n'a encore été prise (la file vient de démarrer aujourd'hui), donc ce rapport retournera "pas assez de données" pendant un moment, honnêtement, jamais un chiffre inventé pour paraître utile plus tôt.
`signal_cascade_convergence.py`/`tests/test_signal_cascade_convergence.py` — 7 nouveaux tests (prix capturé à la décision, échec de lookup n'empêche jamais la décision, remplissage paresseux respecte les fenêtres 24h/7j, une ligne déjà remplie n'est jamais réécrite, rapport honnête sous le seuil minimum, détection correcte d'un critère utile avec échantillons suffisants). [CODE] Sujet : gate anti-usurpation -- refuse un 'validated' si le site déclaré ne confirme pas le contrat

Recreusé après une contestation opérateur légitime sur kVCM ("je vois pas sur X et sur le site web l'équipe écrire ce contrat") : le premier verdict s'appuyait sur des agrégateurs tiers (CoinGecko/BaseScan), pas une preuve directe de l'équipe -- corrigé en creusant `docs.klimaprotocol.com` (même domaine officiel), qui liste bien l'adresse exacte en clair.
Solution : `skills/website_substance.py` -- `gather_website_substance_facts` accepte désormais `contract=`, calcule `contract_confirmed` (substring insensible à la casse sur le contenu BRUT déjà crawlé par Tavily, zéro coût réseau supplémentaire) -- calculé même si le contenu est trop mince pour un score de substance (un lien de swap direct peut être la SEULE chose sur une page minimale, cas réel messyvirgo.com). Propagé par `signal_cascade_web.py` jusqu'à `signal_cascade_convergence.record_source_signal(..., contract_confirmed_on_site=...)`, stocké par token (colonne 'web' uniquement -- seule source qui lit du contenu réel) puis agrégé sur la ligne de la file de triage. **Le vrai gate** : `record_triage_decision(..., decision='validated', ...)` REFUSE désormais (retourne `False`, log WARNING) si `contract_confirmed_on_site == False` (site crawlé, contrat absent) SAUF `override_unconfirmed_contract=True` explicite -- jamais un blocage silencieux ni une automatisation aveugle : le check ne scanne qu'UNE URL déclarée, une confirmation légitime peut vivre sur un sous-domaine jamais crawlé (cas réel kVCM/docs.klimaprotocol.com) -- l'override existe précisément pour ce cas après vérification manuelle, jamais un contournement systématique. Hook `signal-cascade-queue-reminder.sh` étendu pour afficher le statut de confirmation à chaque session.
