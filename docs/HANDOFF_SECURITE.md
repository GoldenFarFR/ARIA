[DEPLOYE] Subject : RPC provider keys were reaching the log files through exception messages -- one filter instead of 214 call-site edits
Date : 2026.08.23 / Probleme : two `429 Too Many Requests` lines logged the full Chainstack RPC endpoint, access key included, caught live while checking a service restart. httpx puts the request URL in its exception message and the code logs the exception, so the credential arrives from INSIDE the error, not from the call site. Counted across the two files that carry it: 5741 occurrences of the Chainstack key and 58234 of a Helius `api-key=`. Nothing had reached git (verified with a repo-wide search) -- local-disk exposure only, but those logs are read by crons and by Claude Code sessions, and it breaks the dome's own standing rule. A partial fix from 20/08 was already in place and closed exactly HALF the hole: routing httpx to WARNING hid the URL of successful calls, while errors carry the same URL and errors are precisely what WARNING lets through.
Solution : `log_redaction.py` -- a pure `redact_secrets()` (sensitive query params, long hex path segments as used by Chainstack, bearer tokens) plus a `logging.Filter` installed on the ROOT logger's handlers, so it sees every record propagated up from `aria_core.services.*` and from third-party libraries alike. Chosen over patching the 214 sites that log a raw exception because those sites are all legitimate and a single one missed tomorrow re-leaks the key. Deliberately conservative: a Solana address is base58 and stays readable (the hex path rule is bounded at 24+ chars), and the diagnosable part of the message survives -- "429" and the host remain, only the credential is replaced. Wired at both entry points (`bootstrap.configure` for the backend, `shadow_persistent.py` for the out-of-Docker shadow process, which does not go through bootstrap and was the one leaking). 12 tests, including one that reproduces the exact production line with the secret arriving as a logging ARGUMENT rather than in the format string. NOT DONE, operator's call: rotating the two exposed keys (can break a running pipeline) and purging the existing log files (deleting the evidence of an exposure before it is acknowledged is the wrong default). — `log_redaction.py`, `bootstrap.py`, `tests/test_log_redaction.py`.

[CODE] Subject : real secret leak via Settings() repr in a failing test -- redacted by field name, not by value sniffing
Date : 2026.08.14 / Problem : while building the /internal/diagnose/wallet-sourcing endpoint (TDD), a test made `Settings()` raise before the new field existed -- pytest's traceback printed the FULL repr of pydantic's exception context, which included every real secret loaded from the actual prod `.env` (admin_api_secret, deploy_activation_secret, telegram_bot_token, telegram_webhook_secret, every LLM key, every X token, github_token, aria_brain_github_token, deepseek_api_key -- all of them, in clear text, into the session's visible output). Root cause: `Settings` never customized `__repr__`/`__repr_args__`, so pydantic's default shows every field's raw value; the module-level `settings` singleton loads the real `.env`, so ANY future exception or debug print touching it repeats the leak, not just this one test.
Solution : `Settings.__repr_args__` overridden to redact any field whose NAME contains "key"/"secret"/"token"/"password" (never sniffs the value -- an empty secret still redacts, so a blank field never masquerades as "not sensitive"), replacing the value with `***REDACTED***` while leaving every non-sensitive field visible for normal debugging. Covers both `repr()` and `str()` (pydantic v2 routes both through `__repr_args__`), so it protects every future call site, not just the one that triggered this incident -- exceptions, `print(settings)`, log lines, anything. `app/config.py`, `tests/test_settings_repr_redaction.py` (3 new tests: leak-free on the 5 secrets involved in the real incident, non-sensitive fields still visible, redaction keyed on name not on value content). Full backend suite green (299 passed) after this change. Operator informed live, recommended rotating every secret listed above since they appeared in the session's visible output before this fix landed.

[DEPLOYE] Subject : backlog #275 audited against the real Claude Code permissions doc -- residual gap closed with an explicit PATH pin, not a live exploit
Date : 2026.08.10 / Problem : #275 (CVE-2026-22708, Cursor -- an allowlisted command like `git` can be hijacked by poisoning PATH/LD_PRELOAD/LD_LIBRARY_PATH via shell builtins the allowlist doesn't itself gate). `research-log-promotion.sh` is the one ARIA cron that scopes Bash to `git *` to commit/push -- checked against the ACTUAL official doc (code.claude.com/docs/en/permissions.md) rather than assumed from the CVE's Cursor-specific writeup, via a single scoped claude-code-guide query (not a broad research fan-out).
Solution : confirmed Claude Code matches the FULL command line, not a naive prefix -- each sub-command of a chain (`&&`/`;`/`|`) must independently match the allow pattern, so `git status && export PATH=/tmp/evil:$PATH` is rejected outright (the agent's own allowed actions can never successfully poison its own environment). The one real residual gap: the scoping does NOT isolate the shell environment ACROSS calls -- an already-poisoned PATH/LD_PRELOAD from an unrelated HOST-level compromise (never from this agent's own reach) would still be inherited by a later `git` call. Cron's ambient env is already minimal (no `.bashrc`/`.profile` sourced), so this was low-probability defense-in-depth, not a live exploit. Fixed by pinning `PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"` and `unset LD_PRELOAD LD_LIBRARY_PATH` explicitly at the top of the script, rather than trusting whatever cron happens to hand it. `bash -n` syntax-checked; not python, no pytest suite applies. — `scripts/research-log-promotion.sh`.
