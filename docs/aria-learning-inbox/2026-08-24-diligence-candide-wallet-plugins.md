# Candide Wallet plugin suite — due diligence beyond Allowance

Spot-check of a colleague's pass on Candide's plugin catalogue (`docs.candide.dev/wallet/plugins/`), re-fetched directly against the live docs, GitHub source, and ARIA's own code. The catalogue is confirmed complete at 3 categories under "Safe Account Plugins" (Passkeys, Account Recovery, Allowance) plus one unrelated top-level product (Forwarding Address, a hosted cross-chain deposit router — inbound-only, not relevant to ARIA's fixed-destination outbound transfer pattern, correctly left out of the original pass). Ranked most to least relevant to ARIA below.

## Account Recovery — Personal Guardians (SocialRecoveryModule) — MAYBE, confirmed and strengthened

Verified directly against `SocialRecoveryModule.sol` (`candidelabs/candide-contracts`): the module exposes plain external functions (`confirmRecovery`, `multiConfirmRecovery`, `executeRecovery`, `finalizeRecovery`, `cancelRecovery`) with zero dependency on ERC-4337, EntryPoint, UserOperations, or a Bundler — guardians call it via standard Ethereum transactions, EIP-712 signatures collected off-chain and submitted in one call. Same integration shape as the already-adopted AllowanceModule: no Candide SDK, no TypeScript, callable from ARIA's existing Python/web3 stack. Provenance is stronger than the original pass implied: the Safe Foundation blog confirms the Safe{Core} team "conducted a thorough evaluation and formal verification before integrating it into our ecosystem," on top of the independent Ackee Blockchain audit and a Certora formal-verification suite in the repo — a real review chain, even though the contract itself is Candide-authored rather than a `safe-global` original like AllowanceModule.

The genuine-gap question checked against ARIA's existing stack (GoPlus, wallet_guard, kill-switch, on-chain AllowanceModule caps): none of those restore access to a Safe whose controlling key is lost outright — the kill-switch stops spending, it doesn't recover control. But the size of that gap depends on an architecture detail worth surfacing: `safe_robinhood_deploy.py`'s own docstring states that for the current testnet pilot "the SAME key acts as both the Safe owner and the allowance delegate... a future real pilot needs the owner key and the agent (delegate) key to be genuinely separate." Today, with owner and delegate collapsed into one key, losing that single key means total lockout — exactly the scenario Personal Guardians would mitigate, so the gap is real right now. Once the planned owner/delegate separation ships, an owner key held separately (colder, backed up) would let the operator simply revoke and replace a lost delegate key via a normal Safe transaction, without needing any recovery module — narrowing or closing the gap Candide would fill. The original MAYBE verdict and its trigger (revisit past the $2-25 pilot tier, or once a single key loss would represent more than a trivial sum) both hold, with one addition: also revisit if/when the owner/delegate key separation lands, since that alone might make this module unnecessary.

## Account Recovery — Candide Guardian (hosted email/SMS) — NO, confirmed

Verified against the live recovery-with-guardians page: the hosted option is real and distinct from Personal Guardians — "Candide signs after email/SMS OTP," no key management required on the user's side. This is a genuine second option in the catalogue, not an invented one. The reasoning for NO holds independent of the recovery-need question above: it introduces a centralized, Candide-hosted trust dependency for authorizing account changes, which conflicts with ARIA's "wallet dédié et isolé, zéro tiers de confiance sur la garde" posture. Even if Personal Guardians is later adopted for the single-key-lockout gap above, the guardians in that scheme would be ARIA/operator-controlled addresses, never Candide's hosted OTP service.

## Passkeys — NO, confirmed

Verified against the live Passkeys docs: the plugin wraps the official `safe-global/safe-modules` Safe Passkeys contracts ("developed by the Safe Protocol Team," audits in that repo) rather than proprietary Candide code, and using it requires the full UserOperation/Bundler flow ("Create and Sign a UserOperation," "Send the signed UserOperation to the bundler"). Both claims in the original pass check out. The verdict stands for the reason given: this solves human biometric authentication to a wallet UI, a problem ARIA's Python agent — which holds and signs with delegated keys programmatically, no human login step — does not have. It would also reintroduce the Bundler/ERC-4337 dependency ARIA already rejected for Allowance, for zero benefit.

## Allowance — baseline, unchanged

Not a new candidate; kept here only as context. The official `safe-global` AllowanceModule is already integrated directly via `execTransaction`, bypassing Candide's `abstractionkit` SDK entirely. Checking the SDK docs directly confirms why that bypass was correct: the documented Allowance flow assumes the TypeScript SDK and a Bundler-submitted UserOperation throughout — nothing in Candide's own docs describes the direct-contract-call path ARIA actually uses, meaning ARIA's integration is already ahead of what the SDK docs demonstrate, not missing something the SDK would have added.

## Overall recommendation

Nothing to integrate right now. The "call the official Safe module directly, skip the Candide SDK/Bundler" approach remains correct across the board — it's precisely why Personal Guardians (also SDK/Bundler-free) is a plausible future fit while Passkeys (Bundler-bound) is not. The one actionable item is process, not code: before revisiting Personal Guardians at a higher capital tier, first check whether the planned owner/delegate key separation has shipped, since that alone may close the lockout gap this module would otherwise solve.
