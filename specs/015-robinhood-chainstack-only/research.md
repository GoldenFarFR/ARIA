# Research: Robinhood Chainstack-Only Sourcing

## Real call chain, traced (not assumed)

`discovery -> candidate -> qualification -> price/liquidity -> regime`, verified against the live code, not the module docstrings (which pre-date the 24-27/08 websocket work and are stale in places):

1. **`robinhood_discovery_loop`** (`/opt/aria-data/solana-robinhood-shadow/shadow_persistent.py`, outside the git repo) fetches `pools` either from `_ROBINHOOD_DISCOVERY_FEED.check_candidates(...)` (on-chain, primary, confirmed active in prod) or a DexPaprika `get_trending_pools` fallback when the feed's env var is unset (confirmed unset today -- the primary feed IS configured, `ARIA_ROBINHOOD_RPC_URL`/`ARIA_ROBINHOOD_RPC_WS` both present). Hands `pools` to `robinhood_pump_shadow.record_signals(pools, chain="robinhood", entry_mode="day_zero")` and `robinhood_pump_v2_shadow.record_signals(...)` (same `pools`, no second fetch).
2. **`record_signals`** (`robinhood_pump_shadow.py:786`) makes **zero network calls of its own** -- it only reads fields already populated on the `TrendingPool` objects it receives (`price_usd`, `reserve_usd`, `pool_created_at`, `transactions_m15`). All filtering (age, liquidity floor, RWA exclusion, dedupe, pocket cap, regime, DeFiLlama chain regime, discovery-only) operates on data already resolved upstream. **Conclusion: nothing to change in `record_signals` itself** -- the real work is entirely in what resolves `pools` before this function sees them.
3. **`OnChainPoolDiscoveryFeed.check_candidates`** (`services/onchain_pool_discovery.py:347`) -- **this is the real finding of this research pass**. It is NOT purely on-chain today despite being "the primary Chainstack feed": for each pending candidate it first tries `self._ws_feed.get_snapshot(key)` (100% Chainstack, no external call) but when that snapshot has no `reserve_usd` yet -- **the common case for a pool that has just been created and has not yet produced a Sync/Swap event** -- it falls through to `dexpaprika.get_pool_reserve_usd(key, network=self.chain)` (line 421), then, if price is still unresolved, `dexpaprika._get_json(f"/networks/{chain}/pools/{key}")` (line 426). This is a genuine transitive dependency invisible to a file-level grep on the two target pocket files, and it is the direct, confirmed cause of `qualified_this_cycle=0` since the 402 outage began (system_issues #269): every day-zero candidate without an observed on-chain event yet is unconditionally routed through the now-broken provider. `dexpaprika._resolve_base_token` (line 443) is called only for already-QUALIFIED candidates, purely to resolve a display symbol -- it never gates qualification.
4. **`evaluate_open_signals`** (pass 2, `robinhood_pump_shadow.py:1146`) calls `_snapshot_with_fallback(client, ..., chain=chain)` **without ever passing `ws_feed`** -- confirmed by reading the call site (line 1199-1201), unlike `advance_exit_simulation` (pass 3, line 1384-1387) which does pass `ws_feed=ws_feed`. Pass 2 therefore never benefits from the Chainstack websocket at all and depends entirely on the DexScreener-first / GeckoTerminal-backfill / DexPaprika-backfill cascade inside `_snapshot_with_fallback`.
5. **`_snapshot_with_fallback`** (`robinhood_pump_shadow.py:1056`) is the pocket's one shared price/liquidity resolver, used by both pass 2 and pass 3. Real cascade, in order: (a) `ws_feed` (Chainstack, when passed and tracking the pool) -- price AND reserve; (b) DexScreener `fetch_token_pairs` -- price, authoritative when available; (c) GeckoTerminal `client.get_pool_snapshot` -- **reserve-only backfill**, triggered only when DexScreener itself reports `liquidity_unknown`; (d) DexPaprika `get_pool_reserve_usd` -- reserve-only backfill, last resort, triggered only when (c) also failed; (e) if `token_address` is falsy (no DexScreener lookup possible at all), falls through to `client.get_pool_snapshot` (GeckoTerminal) as the **sole** source. Both (c)/(d)/(e) are confirmed live code paths, not dead code -- they fire whenever DexScreener's liquidity read is unknown, which is common on a fresh pool.
6. **GeckoTerminal in general** (`from aria_core.services.geckoterminal import ...` in both target files): confirmed **zero calls to the module-level `geckoterminal_client` instance outside `_snapshot_with_fallback`'s step (c)/(e) above**. The bulk of the import (`TrendingPool`, `PoolSnapshot`, `OHLCVResult` dataclasses) is type-only. `v2` (`robinhood_pump_v2_shadow.py`) imports the same types but makes no DexPaprika/GeckoTerminal call of its own -- it reuses `record_signals`'s already-resolved `pools` (its own module comment confirms: "loop already pulls dexpaprika.get_trending_pools, no second network [call]").

## Decision: what actually needs to change

- **Decision**: Add a targeted on-chain reserve/price resolver (direct `eth_call` against the pool contract -- `getReserves()` for Uniswap v2 / Aerodrome classic, `slot0()` + active liquidity for v3/v4, matching what the websocket decoder already extracts from a live `Sync`/`Swap` event) and use it to replace DexPaprika's role at every one of the 4 call sites found above (`check_candidates`'s reserve fallback, its price-detail fallback, `_snapshot_with_fallback`'s GeckoTerminal/DexPaprika reserve backfills, and its GeckoTerminal-only final fallback). A symbol resolver (plain ERC-20 `symbol()`/`name()` eth_call) replaces `_resolve_base_token`.
  - **Rationale**: this is the pattern a peer session (obv-ao-screener) already validated in production for the identical problem (targeted `eth_call` on an already-qualified pool, confirmed 28/08) -- reuse over invention, per this dome's own coherence doctrine. It also directly explains and fixes the pocket's actual outage (candidates stuck at `qualified_this_cycle=0` specifically because they lack a Sync/Swap event yet, exactly the gap a direct reserve read closes).
  - **Alternatives considered**: (a) wait longer before giving up on the websocket (raise `_RECHECK_INTERVAL_SECONDS`/`_OBSERVATION_WINDOW_SECONDS`) -- rejected, this only delays qualification for pools that may never produce a swap within the window, it doesn't remove the DexPaprika dependency FR-001 requires removing; (b) keep DexPaprika as a reserve-only fallback (its role is narrow) -- rejected, explicitly out of scope per the operator's own confirmed instruction ("supprime toutes reference a gecko ou dexpaprika", not "narrow the reliance").
- **Decision**: wire `ws_feed` into `evaluate_open_signals` (pass 2) the same way `advance_exit_simulation` already receives it, so pass 2 also benefits from the Chainstack-first path rather than depending solely on the DexScreener/GeckoTerminal/DexPaprika cascade.
  - **Rationale**: pass 2 is the pocket's only out-of-sample forward-measurement pass; leaving it on the old cascade after this feature would silently keep a GeckoTerminal dependency alive in the one place FR-002 explicitly disallows it.
- **Decision**: `robinhood_pump_v2_shadow.py` needs no dedicated fix beyond its type-only GeckoTerminal import staying type-only (already true) -- it inherits the fix transitively via `record_signals`/`_snapshot_with_fallback`/`evaluate_open_signals`/`advance_exit_simulation`, all defined once in v1 and reused, not duplicated.
  - **Rationale**: confirmed no independent network call exists in v2; duplicating the fix there would violate this dome's "never duplicate a client" norm.

## FR-009: subscription/RPC throttle, measured not guessed

Measured live (not simulated) from `shadow_persistent.log`, `onchain_pool_discovery[robinhood]` lines, 2026-08-28 12:20-16:10 (230.4 real minutes, current window, DexPaprika still down -- this measures the raw discovery/subscription rate, which is **already independent of whether pricing succeeds**: `_register_candidate`'s `add_pool`/websocket subscription fires on every raw on-chain notification, before any DexPaprika call is ever reached):

- `raw_notifications_seen`: 349 -> 1861 (delta 1512) => **~6.56 new pool notifications/minute** (~394/hour).
- `_OBSERVATION_WINDOW_SECONDS = 600.0` (10 minutes): each candidate is tracked (websocket subscription open) for up to this long before expiring.
- **Estimated steady-state concurrent subscriptions**: rate x window ~= 6.56 x 10 ~= **~66 pools concurrently tracked** under today's (degraded) conditions. This is a lower bound: once DexPaprika's 402s stop silently starving `qualified_this_cycle` (today it is 0, meaning positions never actually open downstream, but the raw subscription count itself is NOT gated by that -- confirmed above), the true concurrent count should not change materially, since subscription opening happens at raw-notification time, not at qualification time.
- `eth_call` count per pool during qualification (today, DexPaprika-dependent): up to 3 per pool needing a fallback (`get_pool_reserve_usd`, `_get_json`, `_resolve_base_token` if it qualifies) -- **Decision**: the replacement direct on-chain reads should target the same order-of-magnitude cost (1-2 calls per pool needing the fallback: one reserve read, one symbol read only on actual qualification), never more calls than the DexPaprika path it replaces.
- **Decision (cap)**: set the new subscription/RPC cap at **150 concurrent tracked pools** (~2.3x the measured ~66) with explicit `skip/defer` behavior (a raw notification past the cap is dropped for this pass, logged, and can be picked up on a later notification of the same pool if it re-qualifies before its own window expires) -- never an unbounded burst. This number must be re-measured once DexPaprika is fully removed and real qualification resumes (the 402 outage may be suppressing genuine demand that a working pipeline would reveal); treat 150 as a starting cap to validate in Phase D, not a permanent constant.
  - **Rationale**: 2.3x headroom absorbs the traffic spike expected once qualification (not just detection) starts succeeding again, without leaving the cap so high it stops being a real bound. **Alternatives considered**: an uncapped design (rejected outright -- this dome's own resource-budget doctrine, and the peer session's own 27/08 incident, both explicitly disallow it); a cap derived purely from Chainstack's documented rate limit (rejected as a sole basis -- CLAUDE.md's own doctrine requires empirical measurement over documentation alone, and Chainstack's plan-specific RU budget for this dome is tracked separately in `chainstack_ru_budget.py`, already shared/coordinated infrastructure this feature must reuse, not duplicate).

## SC-002: price provenance, currently not traceable -- gap found

`EVMSwapSnapshot` (`services/evm_swap_ws.py:217`) exposes `price_usd`/`reserve_usd`/`raw_liquidity`/`swap_count`/`cumulative_volume_quote` but **no `tx_hash`/`block_number`/`log_index`** -- confirmed by reading the full dataclass. The underlying decoded event almost certainly carries this data (a standard `eth_subscribe("logs")` push includes `transactionHash`/`blockNumber`/`logIndex` before being decoded into `EVMSwapSnapshot`), it is simply discarded today, same class of "already available, never persisted" gap CLAUDE.md's Doctrine d'Ingestion names.

- **Decision**: add `tx_hash: str | None` and `block_number: int | None` fields to `EVMSwapSnapshot` (log_index optional/nice-to-have, not required for SC-002's own bar), populated from the already-received event payload at zero extra RPC cost, and persist them on the pocket's own row (`robinhood_pump_shadow_log`) at entry so SC-002 becomes mechanically checkable ("every accepted price has a non-null tx_hash") rather than inspected by hand.
  - **Rationale**: this is exactly the "instrument the collection immediately" branch of the Doctrine d'Ingestion (CLAUDE.md) applied to a verifiability requirement instead of a strategy signal -- same principle, and the data is already flowing through the code that needs one added field.
  - **Alternatives considered**: skip provenance entirely, verify SC-002 by manual spot-check in Phase D only (rejected -- the operator's own message explicitly wants SC-002 "verifiable mechanically... rather than by inspection").

## SC-004: DexPaprika-era thresholds, quantity review (not value change)

- **`MIN_LIQUIDITY_USD = 4000.0`** (line 227): comment confirms calibration "on the DexPaprika 'trending pools' population" -- i.e. `reserve_usd` as DexPaprika reports it for an established pool.
- **`MIN_LIQUIDITY_USD_DAY_ZERO = 200.0`** (line 257): comment confirms calibration against `fresh_launch_pretrade_gate_log`'s `reserve_usd` column, sourced from the SAME mixed websocket-then-DexPaprika-fallback path this feature is about to change -- so today's 200.0 already reflects a blend of both sources, not a pure DexPaprika figure.
- **`MAX_POOL_AGE_MINUTES = 10.0`**: a pure time duration, not derived from any provider's data shape -- out of SC-004's scope (nothing to review).
- **Finding**: `reserve_usd`, whether resolved via DexPaprika's indexer or a direct on-chain reserve read, is defined as the same real-world quantity -- the USD value of a pool's on-chain reserves at a point in time. DexPaprika does not compute a differently-shaped number; it re-derives the same on-chain fact through its own indexing pipeline, at whatever latency that pipeline has. **This is a quantity match, not a value match** -- the two numbers can differ slightly at the exact same instant purely from indexing latency (DexPaprika's own docs note up to ~15s staleness on its free tier, noted in a prior session's research on this exact provider), not from measuring something different.
  - **Decision**: keep both threshold VALUES unchanged for this feature. Add the Phase D worked-example comparison (old DexPaprika-era reading vs. new on-chain reading, same real pool) as the mechanical proof this finding holds, per the operator's explicit gate -- and if that comparison surfaces a real quantity mismatch (not just latency-driven noise), stop and report it to the operator rather than silently picking a new number, exactly as instructed.
