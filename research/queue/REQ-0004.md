# REQ-0004 -- Full audit of the live<->backfill join keys

    issued by: Claude B, relaying an operator request, 2026-09-02 -- priority P0
    engraved by: Claude A
    status: OPEN (REQ-0001 covered pool_id, topics, tx_hash only)

## Request

Audit every join key between the live and backfill paths: `pool_id`, `token`,
`chain`, `tx_hash`, `log_index`, `block_number`, timestamp. Plus a permanent
schema-compatibility test asserting that LIVE->RAW and BACKFILL->RAW join without
loss.

## The risk class, named by B

**Syntactically valid, semantically incompatible identifiers.** The program runs,
the data arrives, it never joins, and nothing fails. A test comparing the two
paths is the only defence. REQ-0001 was the first instance found; there is no
reason to assume it was the only one.

## The case A confirms is NOT covered by the REQ-0001 fix

The live path writes `token=""` on purpose (`_TrackedPool` does not carry the
token address, and inventing one would put a guess in the raw table). The backfill
writes a real token. Any aggregate grouping by token would therefore split live
from backfill rows.

This is a different family from REQ-0001 and needs a different defence:
REQ-0001 was "same value, different shape", curable by normalisation. This is
"empty versus filled", which normalisation cannot fix. Today it is harmless
because everything joins on `pool_id`; it stops being harmless the day one
aggregate groups by token.
