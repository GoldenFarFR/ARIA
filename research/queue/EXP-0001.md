## Why this first, and not something else

Every open question in this project is currently blocked by the same thing: we do
not have a sample. Measured state of `onchain_replay_raw` on 2026-09-02:

    189,062 events | 9 pools | 1 chain | 3 event types
    one pool carries 151,916 of those events
    14,068 distinct wallets, 910 on >=2 pools, 169 on >=3, 8 on >=5
    one pool (0xd89f6933a8, 9,191 events) carries NO tx_sender at all

With 9 pools, one of them dominant, the actor graph proves nothing structural, so
PVP is not ready either. H9 cannot go out-of-sample: the register states the
effective n is close to 2.

The blocking cost is acquisition. Backfilling one token measured **90,948 RU**
(AI), and the register notes backfill cost follows activity, not duration. Twenty
out-of-sample tokens is ~1.8M RU against a 650k/day cap. Not viable.

Measured alternative, probed against the live endpoint on 2026-09-02:

| | Robinhood | Base |
|---|---|---|
| block time | 0.11 s | 2.0 s |
| pool births | ~1,090/hour | ~126/hour |
| chain-wide swaps | ~277,000/hour | ~13,785/hour |
| births that traded within 18 min | 115 of 333 (34.5%) | not measured |

Cost of a 60 s filtered poll on the Initialize topic: **1,440 RU/day**, 0.2% of
cap. Cost of subscribing to the whole PoolManager: ~6.65M RU/day, cap gone in
2h20. And the decisive property, verified: **the v4 Swap signature indexes the
pool id in topic1, and the endpoint accepts a LIST there** -- one request watched
333 pools at once (7.98 s, 29,674 swaps returned). Watch-tier cost scales with
poll frequency, never with the number of pools watched.

The methodological argument matters more than the cost one. A backfill can only
select tokens we already know about, therefore survivors -- AI and MEOW were
chosen after the fact. A cohort captured at T0 also contains the ~65% of newborns
that never trade. That is the difference between a survivorship-biased sample and
a cohort, and it is what will make H9 testable honestly.

## Hypothesis (instrument, not market)

**H-INST-1**: a periodic `eth_getLogs` filtered on the Initialize topic captures
100% of pool births on a chain, at under 2,000 RU/day/chain, with a median
birth-to-persisted latency under 90 s.

Falsifiable, and the failure criteria below are fixed before any result.

## Allowed data

`eth_getLogs` against each chain's PoolManager, Initialize topic only. Block
range never above 10,000 per request (measured limit: 10,000 accepted, 20,000
refused). No third-party paid source. No X. Read-only on chain.

## Method

1. Polling loop with a **persisted block cursor**, so a restart leaves no hole.
2. Each birth written with an **immutable T0** (block number and block timestamp,
   never wall-clock as the event time). Three clocks stay distinct and separately
   stored: `event_time`, `observed_at`, `persisted_at`.
3. Never write to `aria.db` or `shadow.db` -- see PROTOCOL.md, incident 17/08.
   Use a dedicated file under `research/`.
4. RU accounted through `chainstack_ru_budget.record_usage_fast`, never a
   home-made counter, and gated on `can_spend(chain)` like every other consumer.

## Controls (not optional)

- **Completeness**: replay an already-covered window with an independent request
  and compare set to set. Zero tolerance on identity (tx_hash, log_index, block).
- **Gap**: the union of covered block ranges must be contiguous over the whole run.
- **Restart**: kill the process mid-run, confirm no birth is lost across the seam.
- **Negative control**: run the same query on a window with no PoolManager
  activity and confirm it returns empty rather than something plausible.

## Success criteria (frozen before the experiment)

- block coverage 100%, zero unexplained gap
- event identity 100% on the control sample
- measured cost <= 2,000 RU/day/chain
- median birth-to-persisted latency <= 90 s
- no guardrail file touched, no deployment, no daemon left running

## Failure criteria (frozen before the experiment)

- a single unexplained block gap -> REJECT
- cost > 5,000 RU/day/chain -> REJECT, the instrument costs more than it is worth
- median latency > 5 min -> MORE_DATA, usable for the slow regime only, and that
  limitation must be written down rather than averaged away

## Resource budget

**20,000 RU total**, construction and measurement included, across both chains.
Stop and report at the ceiling rather than asking for more mid-run.

## Secondary measurement (free, same data)

What fraction of newborn pools records at least one swap in their first 18
minutes? Reference point: 115/333 = 34.5%, **one window, one instant, one chain**.
Confirm across several windows and several distinct days, and state the number of
distinct days covered -- a rate measured on a single day is not a rate.

## Hard bounds

Read-only on chain. This never becomes a permanent daemon without an explicit
operator go: the kill-switch has been armed since 12:34:57 today and every shadow
loop is paused, so adding a continuous RU consumer is the operator's decision,
not ours. Deliver the instrument and the measurement; leave the wiring proposal
in the result.
